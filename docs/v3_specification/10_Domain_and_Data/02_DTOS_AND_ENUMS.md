## 1. Conventions

- **Records.** Every record is declared `class Name(msgspec.Struct, frozen=True, kw_only=True, gc=False)`. `frozen` makes instances immutable, `kw_only` forces keyword construction, `gc=False` opts the instances out of cyclic garbage collection (the records hold no reference cycles).
- **Enumerations.** Every closed value domain is a `StrEnum`; the member value is the lowercase or snake_case string stored in the database and emitted in YAML and exports.
- **Optionality.** A field typed `X | None` is optional; a field without `| None` is required. A `default=` makes a field optional at construction but the field still always carries a concrete value.
- **Timestamps.** Timestamps cross boundaries as ISO-8601 UTC strings (`str`). The persistence layer stores them verbatim.
- **No implementation code.** This document defines structure, types, optionality, defaults, and constraints. It defines no function bodies.

## 2. Type aliases

```python
type RunId = int               # auto-incrementing; always > 0
type ResultId = int            # auto-incrementing; always > 0

type ProviderId = str          # INTERNAL; UUID4 textual representation (e.g. "a3b8c1d2-7f04-4b8e-9c1d-2e5f0a1b3c4d"); auto-generated by ProvidersStore on insert; never user-entered; never displayed in the UI (DD-33)

type SettingKey = str          # dotted key, e.g. "benchmark.retry_count"
type Iso8601Utc = str          # ISO-8601 timestamp in UTC, e.g. "2026-05-22T14:53:09Z"
```

A benchmark target is always the pair `(ProviderId, ModelName)`; the application never identifies a target by `ModelName` alone.

## 4. Enumerations

### 4.1 RunMode

```python
class RunMode(StrEnum):
    SYNTHETIC = "synthetic"
    TASKS     = "tasks"
    GRADED    = "graded"
```

The three — and only three — run modes.

| Member      | Meaning                                                                                                                                                                                                                                                                                         |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SYNTHETIC` | Runs synthetic tasks generated from an input/output size matrix; measures timing and throughput only; **no grading**.                                                                                                                                                                           |
| `TASKS`     | Runs real tasks loaded from user task files; measures timing and throughput only; **no grading**. Task Benchmark never grades — it is identical to `SYNTHETIC` in every grading dimension; the only difference between them is the prompt source (user files vs synthetic size-matrix prompts). |
| `GRADED`    | Runs real tasks through the full evaluation pipeline (inference, keyword check, cosine check, judge check). The only mode that grades.                                                                                                                                                          |

The grading-related fields on `BenchmarkResult` — `verdict`, the per-phase verdicts (`keyword_verdict`, `cosine_verdict`, `judge_verdict`), `cosine_similarity`, `resolution_layer`, and the per-term records — are populated only on `GRADED` runs. On every `TASKS` and every `SYNTHETIC` result those fields remain null/absent, identically.

**Used by:** `BenchmarkRun.run_mode`, `RunStartRequest.run_mode`, the mode-visibility policy, the run-summary dialog. **Persisted in:** `benchmark_runs.run_mode`.

### 4.2 RunStatus

```python
class RunStatus(StrEnum):
    INCOMPLETE = "incomplete"
    COMPLETED  = "completed"
    FAILED     = "failed"
    STOPPED    = "stopped"
```

The four — and only four — **persisted** run statuses.

| Member       | Meaning                                                                                                                                                                                                                                 |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INCOMPLETE` | The run has been created and has results that have not all reached a terminal status. This is the status of a run that is created, that is in progress (the pipeline derives the finer in-memory state), or that crashed mid-execution. |
| `COMPLETED`  | Every result reached a terminal status and the run finished normally.                                                                                                                                                                   |
| `FAILED`     | A fatal pipeline error halted the run.                                                                                                                                                                                                  |
| `STOPPED`    | The user stopped the run before completion.                                                                                                                                                                                             |

The transient states `RUNNING` and `PAUSED` are **in-memory-only** derived states maintained by the pipeline while it executes a run. They are never written to `benchmark_runs.status` and are not members of this enum.

**Used by:** `BenchmarkRun.status`. **Persisted in:** `benchmark_runs.status`.

### 4.3 ResultStatus

```python
class ResultStatus(StrEnum):
    PENDING                 = "pending"
    RUNNING_INFERENCE       = "running_inference"
    AWAITING_KEYWORD_CHECK  = "awaiting_keyword_check"
    AWAITING_COSINE_CHECK   = "awaiting_cosine_check"
    AWAITING_JUDGE_CHECK    = "awaiting_judge_check"
    COMPLETED               = "completed"
    FAILED_INFERENCE        = "failed_inference"
    FAILED_PROVIDER         = "failed_provider"
    FAILED_TIMEOUT          = "failed_timeout"
    FAILED_JUDGE_TIMEOUT    = "failed_judge_timeout"
    ERRORED                 = "errored"
```

The per-task lifecycle state of a single `BenchmarkResult`. Eleven members in two groups.

**Pipeline-position states** (the first five) — non-terminal; the result is still moving through the pipeline:

| Member                   | Meaning                                                                                                   |
| ------------------------ | --------------------------------------------------------------------------------------------------------- |
| `PENDING`                | The result row has been created; the task has not started. The reset target for retry and crash recovery. |
| `RUNNING_INFERENCE`      | The inference call for this task is in progress.                                                          |
| `AWAITING_KEYWORD_CHECK` | Inference is done; the result is queued for the keyword phase.                                            |
| `AWAITING_COSINE_CHECK`  | The keyword phase is done; the result is queued for the cosine phase.                                     |
| `AWAITING_JUDGE_CHECK`   | The cosine phase is done; the result is queued for the judge phase.                                       |

**Terminal states** (the last six) — the result will not change further unless explicitly retried:

| Member                 | Meaning                                                                                                                                                                                                                                                                                                                                                                    | Retryable |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| `COMPLETED`            | Every applicable phase ran; the result is final. The `verdict` field is set to `PASS` or `FAIL`.                                                                                                                                                                                                                                                                           | No        |
| `FAILED_INFERENCE`     | The inference call failed irrecoverably (model-side error).                                                                                                                                                                                                                                                                                                                | Yes       |
| `FAILED_PROVIDER`      | The provider was unavailable or rejected the request.                                                                                                                                                                                                                                                                                                                      | Yes       |
| `FAILED_TIMEOUT`       | The inference exceeded its adaptive-timeout budget after all attempts (Phase 2 — test-role inference).                                                                                                                                                                                                                                                                     | Yes       |
| `FAILED_JUDGE_TIMEOUT` | The per-task judge call exhausted its adaptive-timeout budget, OR the judge model was excluded for the remainder of the run after crossing the consecutive-max-timeout threshold (Phase 4 — judge). `verdict` stays `None`; the task is NOT marked `COMPLETED`. See `11_Services_and_Algorithms/07_ADAPTIVE_TIMEOUT.md` for the per-role escalation + exclusion algorithm. | Yes       |
| `ERRORED`              | An unexpected error halted the task.                                                                                                                                                                                                                                                                                                                                       | Yes       |

**Retryable terminal states:** `FAILED_INFERENCE`, `FAILED_PROVIDER`, `FAILED_TIMEOUT`, `FAILED_JUDGE_TIMEOUT`, `ERRORED`. Retry resets these rows **from their failed stage** (DD-66): a `FAILED_JUDGE_TIMEOUT` row (and a judge-stage `ERRORED` row with a response) resets to `AWAITING_JUDGE_CHECK` — the inference response, timing/token metrics, keyword verdict, and cosine score are **preserved** and only the judge re-runs against the same response; every other retryable status resets to `PENDING` for a whole-task re-run. `COMPLETED` is never retried automatically. The persistent JUDGE per-role adaptive-timeout bucket may carry escalated state from the original attempt; the in-run consecutive-timeout count is reset by Resume/Retry.

**Used by:** `BenchmarkResult.status`. **Persisted in:** `benchmark_results.status`.

### 4.4 Verdict

```python
class Verdict(StrEnum):
    PASS = "pass"
    FAIL = "fail"
```

The strictly binary quality outcome of a graded result. There are exactly two members. There is **no** `UNKNOWN` verdict.

| Member | Meaning                                                          |
| ------ | ---------------------------------------------------------------- |
| `PASS` | The graded result satisfied the deciding evaluation layer.       |
| `FAIL` | The graded result did not satisfy the deciding evaluation layer. |

A verdict is null (unset) while a result is pending and is set only when `ResultStatus` reaches `COMPLETED`. A result that ends in a terminal-failure status carries no verdict.

**Used by:** `BenchmarkResult.verdict`, `BenchmarkResult.keyword_verdict`, `BenchmarkResult.cosine_verdict`, `BenchmarkResult.judge_verdict`. **Persisted in:** `benchmark_results.verdict`, `.keyword_verdict`, `.cosine_verdict`, `.judge_verdict` (each nullable).

### 4.10a AdaptiveTimeoutRole

```python
class AdaptiveTimeoutRole(StrEnum):
    INFERENCE     = "inference"      # test-model inference (Phase 2); also sizes the model-switch warmup (DD-64)
    JUDGE         = "judge"          # per-task judge call (Phase 4)
    RUN_ANALYSIS  = "run_analysis"   # user-initiated run-analysis generation — its own bucket (DD-65)
```

Identifies the per-role bucket of the Adaptive Timeout Service. The service keys its persistent and in-run state on `(provider_id, model_name, role)` — a model used as both a test model AND a judge model carries two independent state buckets, and exclusion in one role does NOT affect the other. `RUN_ANALYSIS` is a third, independent bucket (DD-65): the longer run-analysis prompt escalates on its own ladder from its own min, never inheriting the per-task `JUDGE` bucket's learned (often maxed) budget.

| Member      | Meaning                                                                                                                                                                                                                                                                                                                          |
| ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INFERENCE` | The Phase 2 per-task main inference call (test-role model). Uses the `benchmark.min_timeout_seconds` / `benchmark.max_timeout_seconds` / `benchmark.retry_count` / `benchmark.consecutive_max_timeouts_to_exclude` ladder.                                                                                                       |
| `JUDGE`     | The Phase 4 per-task judge call AND the user-initiated run-analysis generation call (both consult the same `(provider_id, model_name, JUDGE)` bucket). Uses the `eval.judge_timeout_min_seconds` / `eval.judge_timeout_max_seconds` / `eval.judge_timeout_escalation_steps` / `eval.judge_timeout_consecutive_threshold` ladder. |

**There is intentionally NO `EMBEDDING`, `PROVIDER_TEST`, or `READINESS` member.** Embedding calls use the FIXED `eval.embedding_timeout_seconds` budget — no adaptive escalation, no exclusion. The Test Inference path (`LLMClient.test_inference`) uses its own fixed 60 s deadline. The readiness probe (`LLMClient.probe_health`) uses its own fixed short deadline. None of those three surfaces consults the Adaptive Timeout Service.

**Used by:** `AdaptiveTimeoutService.next_budget`, `record_success`, `record_timeout`, `is_excluded` (see `08_Cross_Cutting/08-E_interfaces_contracts.md` §17 and `11_Services_and_Algorithms/07_ADAPTIVE_TIMEOUT.md`). **Persisted in:** the per-role state is in-memory only; persistent last-known-good budgets are rebuilt on resume from `BenchmarkResultAttempt` rows the same way the single-role state was, but keyed by role.

### 4.18 InferenceActivity

| `READINESS_PROBE` | The Readiness Service is running a provider or embedding probe. Held for the duration of a probe call.                                  |

**Used by:** `InferenceActivityContext.activity`, `InferenceActivityState.current`, `InferenceActivityStore` (see `08_Cross_Cutting/08-E_interfaces_contracts.md`). **Persisted in:** not persisted; the gate is runtime state only.

Classifies which user-visible LLM-call surface produced an `_inference_progress` event (`08_Cross_Cutting/08-J_event_bus_catalog.md` §5.3, payload `InferenceProgressEvent` — §7.7a below). The four members exhaust the surfaces that emit live progress feedback to the user.

| Member            | Meaning                                                                                                                                                                                                                               |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BENCHMARK_TASK`  | A per-task main inference call inside a benchmark run. Rendered as the Progress widget Current-task "Inference progress" sub-row (`04_Progress_Widget/description.md` §7.1).                                                          |
| `BENCHMARK_JUDGE` | A per-task judge call inside a benchmark run in `GRADED` with the per-task judge phase on. Rendered as the Progress widget Current-task "Judge progress" sub-row (`04_Progress_Widget/description.md` §7.1).                          |
| `RUN_ANALYSIS`    | A user-initiated run-analysis (re)generation issued through the Generate Analysis dialog (`07_Common_Dialogs/generate_analysis_dialog.md`). Rendered as the dialog's live progress line in place of the static "Generating…" spinner. |
| `PROVIDER_TEST`   | A user-initiated Test inference call issued from the Provider Edit sub-dialog (`06_Settings_Dialog/sub_dialogs/provider_edit.md` §8.2). Rendered as the inference-test panel's live indicator in place of the Run-button area.        |

**No `READINESS_PROBE` value exists.** Readiness probes (`LLMClient.probe_health()`, `11_Services_and_Algorithms/09_READINESS_PROBE.md`) are invisible background checks; they NEVER emit `_inference_progress` events and therefore never carry an `InferenceContext`. The enum deliberately excludes that surface so a future probe path cannot leak progress events onto the bus by reusing the type. The same exclusion holds for any other background check that does not surface a live indicator to the user.

**Used by:** `InferenceProgressEvent.context` (§7.7a below) and the shared emitter helper documented in `11_Services_and_Algorithms/04_EVALUATION_PIPELINE.md` §6.9. **Persisted in:** not persisted; the field is runtime-only on the event payload.

### 4.22 CancelLevel

```python
class CancelLevel(StrEnum):
```

### 4.23 CancelReason

```python

    AUTO_PAUSE   = "auto_pause"
    USER_STOP    = "user_stop"
    APP_SHUTDOWN = "app_shutdown"
```

The closed set of reasons a run's `CancellationToken` can be cancelled with (DD-42). The

| Member         | Level | Outcome it derives (see the outcome matrix, `11_Services_and_Algorithms/16_CONCURRENCY_MODEL.md` §6.8) |
| -------------- | ----- | ------------------------------------------------------------------------------------------------------ |

| `APP_SHUTDOWN` | hard  | Persist nothing terminal; run left `INCOMPLETE` for next-launch recovery (D-R-02).                     |

**Used by:** `CancellationToken.cancel(reason=...)`, `CancellationToken.snapshot()`,
`TaskCancelledError`. Never persisted.

## 5. Domain records — catalog

These records map to the catalog tables. They model configuration independent of any run.

### 5.1 ProviderConfig

`ProviderConfig` models one persisted provider catalog row. The `provider_id` is **INTERNAL and AUTO-GENERATED** by `ProvidersStore` on insert; it is a UUID4 textual representation, never user-entered and never displayed in the UI. The user-entered unique display label is `name`; the `providers` table enforces `UNIQUE (name)` and the store pre-checks duplicates via `get_by_name`. The UI surfaces (Settings table, dropdowns, dialogs, event log, exports) render `name`; only the data layer and event payloads use `provider_id`. See DD-33 (`08_Cross_Cutting/08-F_spec_issues_log.md`).

**Invariants.** `name` is non-empty (`NonEmptyStr`) and unique among all `ProviderConfig` rows. The `provider_id` UUID4 is set by the store on `add` and never changes thereafter; a rename mutates only `name`.

### 5.2 Embedding selection (no DTO — two `app_settings` keys)

Per D-R-13 the embedding feature is **one selected `(provider, embedding model)` pair**, not a multi-row named catalog. There is therefore **no `EmbeddingConfig` struct, no `EmbeddingConfigDraft`, no `EmbeddingConfigId`/`EmbeddingConfigIdStr`, and no `EmbeddingConfigStore`** — and no `embedding_configs` table. Embeddings have no user-facing name.

The selection is stored as two `app_settings` keys, read and written via `AppSettingsStore`:

- `embedding.selected_provider_name: str` — the stable provider **name** (not the internal UUID, which regenerates on import; by-name storage is what lets the selection survive export/import — resolves MISS-24).
- `embedding.selected_model_name: str` — the embedding model string.

The per-provider embedding-model list is **dynamic** — discovered from the provider (or its preconfigured list) at display time in the Settings dialog — and is **not** persisted. At use time the pair is resolved to a live provider and model and re-validated by the start-up capability probe (`11_Services_and_Algorithms/06_EMBEDDING_SERVICE.md` §6.6a). When no selection exists or it fails to resolve, `GRADED` is disabled until the user picks a working `(provider, model)` in Settings.

**Where used:** Settings dialog (single pick from the dynamic per-provider list), embedding service, readiness service, run-creation use case (the resolved pair is frozen into `BenchmarkRun.embedding_provider_name` / `BenchmarkRun.embedding_model_name` at run start). **Persistence:** the two `app_settings` keys above (no dedicated table).

`echo_tokens_to_log` controls only UI logging; transport streaming is always used so time-to-first-token can be measured.

`max_output_tokens` is the **maximum completion-token budget** for the call (DD-67). It defaults to **4096** and is sourced from `benchmark.max_output_tokens` for the model under test (`eval.judge_max_completion_tokens` for the judge call), both overridable in Settings → Advanced and the New Benchmark advanced options, and frozen into the run snapshot. The floor is 4096 — Anthropic's SDK **requires** a `max_tokens` value, so the field is always sent; OpenAI-compatible and Gemini clients pass it as their respective max-completion parameter. A reasoning model emits its reasoning into the completion, so a small cap can truncate it before any answer/JSON; 4096 gives a reasoning preamble room (see SPEC-057/DD-67).

`temperature` is **optional** (D-R-04). The `benchmark.temperature` setting **defaults to `0.0`** (DD-61) so models in one run are compared at the same low-variance setting; that value is passed verbatim to the client. The user may set any `≥0.0` value (passed through verbatim, not clamped) or **blank** it — a blank maps to `None`, the client omits the parameter, and the provider's own default applies (models may then differ in effective temperature; the run is flagged not directly comparable). It is sourced from the `benchmark.temperature` setting (Settings → Advanced, overridable per run via the New Benchmark advanced options) and frozen into the run's settings snapshot for reproducibility-of-record. The accepted range and interpretation vary by provider (some `0.0`–`1.0`, some `0.0`–`2.0`); the value is not clamped by the application — leave it blank to use the provider default. No `seed` field is provided: seed support is inconsistent across providers (honoured by local llama.cpp-based backends, best-effort on OpenAI, absent on Anthropic and most Gemini versions), so a seed would give a false impression of determinism; the benchmark targets overall speed and quality rather than fine-tuned sampling reproducibility.

**Where used:** LLM client, inference phase, judge phase.

## 8. Patch records

A patch record carries a partial update to a persisted record. Every field is optional; an unset field leaves the corresponding column unchanged.

### 8.1 ResultPatch

```python
class ResultPatch(msgspec.Struct, frozen=True, kw_only=True, gc=False):
    status: ResultStatus | None = None
    verdict: Verdict | None = None
    started_at: Iso8601Utc | None = None
    finished_at: Iso8601Utc | None = None
    system_prompt_sent: str | None = None
    user_prompt_sent: str | None = None
    raw_response: str | None = None
    sanitized_response: str | None = None
    has_thinking_block: bool | None = None
    response_char_length: NonNegativeInt | None = None
    total_time_ms: DurationMs | None = None
    ttft_ms: DurationMs | None = None
    prompt_tokens: NonNegativeInt | None = None
    completion_tokens: NonNegativeInt | None = None
    tokens_per_second: NonNegativeFloat | None = None
    tokens_estimated: bool = False
    sanity_check_passed: bool | None = None
    keyword_verdict: Verdict | None = None
    cosine_similarity: CosineScore | None = None
    cosine_verdict: Verdict | None = None
    judge_verdict: Verdict | None = None
    judge_reasoning: str | None = None
    judge_time_ms: DurationMs | None = None
    judge_completion_tokens: NonNegativeInt | None = None
    resolution_layer: ResolutionLayer | None = None
    error_kind: ErrorKind | None = None
    error_message: str | None = None
    terms: tuple[BenchmarkResultTerm, ...] | None = None
    attempts: tuple[BenchmarkResultAttempt, ...] | None = None
```

When `terms` or `attempts` is set, the persistence layer replaces all child rows for the result. Identity columns (`result_id`, `run_id`, `task_id`, `provider_id`, `provider_name`, `model_name`, `created_at`) are never patchable; the `provider_name` snapshot is set once at task start and never updated thereafter.

**Where used:** the data store's result-update operation, called by the pipeline after each phase.

### 8.2 RunStatusPatch

```python
class RunStatusPatch(msgspec.Struct, frozen=True, kw_only=True, gc=False):
```

Carries the run-header columns the pipeline updates as a run progresses. `run_id`, `timestamp`, `run_mode`, `total_tasks`, and the snapshot child tables are never patchable. `run_name` is changed only through a dedicated rename operation.

**Where used:** the data store's run-update operation.
