This document maps every edge case in `08_Cross_Cutting/08-I_edge_cases.md` to the test pattern that proves the implementation handles it. Each edge case carries a stable `EC-` identifier; the catalog states the trigger and the expected behaviour, and this document fixes how that behaviour is verified — the test tier, the proving module, and the criterion pattern from `05_ACCEPTANCE_CRITERIA_PATTERNS.md`. Every edge case must appear in some story's `edge_cases:` front-matter and have a passing test, and `03_TRACEABILITY.md`'s validator fails the build on any uncovered `EC-` identifier.

## 1. Purpose and Scope

An edge case is a non-obvious behaviour the implementation must handle. The catalog in `08_Cross_Cutting/08-I_edge_cases.md` states each one; this document is the bridge from that statement to a concrete test. For each `EC-` identifier it answers three questions: what *tier* of test proves it, in which *module* the proving test lives, and which *criterion pattern* the test follows. The tester agent uses this document to derive the test; `03_TRACEABILITY.md`'s validator uses it to confirm no edge case is left unproven.

## 2. Test Tiers and How an Edge Case Is Assigned One

Each edge case is assigned the tier that proves its behaviour with the least scope while still exercising the real concern, following `16_Engineering_Standards/07_TESTING_STANDARD.md`:

| Tier             | Proves an edge case when…                                                                                                                                    | Mechanism                                                                                         |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| **unit**         | The behaviour lives inside one module and is reachable with that module's logic alone — a status transition, a validation rule, a derived-state computation. | A unit test, colocated in the module's `tests/`, often `@pytest.mark.parametrize` (table-driven). |
| **widget**       | The behaviour is a UI affordance — a gated control, a banner, a dialog sequence, a live refresh.                                                             | A `pytest-qt` test driving a real widget.                                                         |
| **integration**  | The behaviour spans several modules and a real local resource — the pipeline plus persistence, the loader plus the filesystem.                               | A test in `tests/integration/` with a `tmp_path` database and the service fakes.                  |
| **property**     | The behaviour is a universal property over an open input space — a round trip, a bound, a count conservation.                                                | A Hypothesis property test, `property`-marked.                                                    |
| **architecture** | The behaviour is a structural guarantee the codebase must hold by construction — a forbidden cross-thread mutation, a forbidden import.                      | An `import-linter` contract or a `pytest-archon` / AST architecture test.                         |

Some edge cases need two tiers — for example a structural guarantee proven by an architecture test *and* a behavioural fallback proven by a unit test. Such cases list both.

## 3. How to Read the Mapping Table

Each row maps one `EC-` identifier:

| Column                   | Meaning                                                                                                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| **EC id**                | The stable identifier from `08_Cross_Cutting/08-I_edge_cases.md`.                                                                                 |
| **Behaviour under test** | A short restatement of what the test must prove. The catalog holds the full statement.                                                            |
| **Tier**                 | The test tier(s) from Section 2.                                                                                                                  |
| **Proving module**       | The module from `01_MODULE_INVENTORY.md` whose `tests/`, or the top-level `tests/` subdirectory, holds the test.                                  |
| **Criterion pattern**    | The acceptance-criterion pattern from `05_ACCEPTANCE_CRITERIA_PATTERNS.md` the proving test follows: Given/When/Then, Table-driven, or Invariant. |

### 19.1 The traceability validator (`validate_traceability.py`)

The validator in `03_TRACEABILITY.md` enforces coverage by reading the **catalogs** as the source of truth, not this mapping:

1. **Collect** `catalog_ids` — every `EC-…` identifier defined across all catalog documents listed above (by scanning their entry headings/rows).
1. **Collect** `mapped_ids` — every `EC-…` identifier that has a row in this mapping; and `story_ids` — every identifier named in some story's `edge_cases:` front-matter.
1. **Fail the pull-request gate** if either set difference is non-empty:
   - `catalog_ids − mapped_ids` is non-empty → an **uncovered** edge case (e.g. *"EC-IMP-5 is defined in IMPORT_FORMATS but has no row in 06_EDGE_CASE_TO_TEST_MAPPING.md"*).
   - `mapped_ids − catalog_ids` is non-empty → a **dangling** mapping row (e.g. *"the mapping cites `EC-FL-404` (illustrative, not a real id), defined in no catalog"*).
   - any catalog id absent from `story_ids` and from the test suite → an **untested** edge case.

Because the validator enumerates from the catalogs, the gate is real and non-circular: adding a catalogued edge case without a mapping row (and a test) fails CI. **This mapping now carries exactly one row per catalogued identifier across all scopes** — every `08-I` case (`EC-RUN-*`, `EC-TASK-*`, `EC-PROV-*` including the `4a–4f` and `5a–5f` sub-cases, `EC-SET-*`, `EC-RES-*`, `EC-LOG-*`, `EC-WS-*`, `EC-PERF-*`, `EC-PERSIST-*`, `EC-PLAT-*`) plus all `EC-IMP-*`, `EC-EXP-*`, `EC-FL-*`, `EC-RD-*`, `EC-M-*`, and `EC-TE-*`. The D-R-08 regeneration is complete; any new catalogued edge case must add its mapping row (and a test) here or the validator will (correctly) report it as uncovered.
