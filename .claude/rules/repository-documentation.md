# Repository Documentation Standards

Source of truth: `docs/v3_specification/14_Process_and_Traceability/02_STORY_FORMAT.md`,
`03_TRACEABILITY.md`, and `04_ADR_FORMAT.md` for the `docs/` structure; general best practice
for the rest. **This document replaces any older doc-structure convention** — this is a
from-scratch rewrite and the `docs/` tree below is authoritative going forward.

## The docs/ tree

```
docs/
├── stories/                  # one file per implementation story — see traceability-and-stories.md
│   └── story-NNN-short-slug.md
├── adr/                       # accepted Architecture Decision Records, MADR 4.0
│   ├── README.md               # the ADR index — see traceability-and-stories.md
│   └── NNNN-short-slug.md
├── v3_specification/          # the vendored specification — READ-ONLY, never edited
│   └── <folder>/<file>.md
├── architecture/
└── development/

traceability.yaml               # GENERATED at repo root next to pyproject.toml — never hand-edited
```

- **`docs/stories/`** — one Markdown file per implementation story, named
  `story-NNN-short-slug.md`. Flat directory, no per-feature subdirectories — the story's
  `modules:` front-matter records which feature it belongs to, not the file location. Full
  format and workflow: `traceability-and-stories.md`.
- **`docs/adr/`** — one Markdown file per accepted ADR, named `NNNN-short-slug.md`, plus a
  `README.md` index table. Full format and lifecycle: `traceability-and-stories.md`.
- **`docs/v3_specification/`** — the vendored specification, copied into the repository at
  bootstrap. It is **read-only**: never edited in place. A change to an accepted spec clause
  that a `done` story depends on requires a new story plus, if architecturally significant, a
  new ADR — never a silent edit to the vendored file.
- **`traceability.yaml`** — generated by `just trace`, validated by `just trace-check`. Never
  hand-edited; a stale or hand-edited copy fails the pull-request gate (see
  `traceability-and-stories.md`).

## Root-level documents

- **`README.md`** — what the project is, how to run it, the tech stack, a quick start, and
  links into `docs/`. Keep it short; move detail into `docs/`.
- **`CHANGELOG.md`** — [Keep a Changelog](https://keepachangelog.com/) format. Entries grouped
  under Added, Changed, Deprecated, Removed, Fixed, Security. New entries accumulate under
  `[Unreleased]` until a release is tagged. Generate an entry when a public API is
  added/changed/deprecated/removed, for a bug fix, or for a security patch. Do **not** generate
  one for an internal refactor, a CI change, or a dev-dependency bump.
- **`LICENSE`** — SPDX identifier matching `pyproject.toml`.

There is one project version, declared once in `pyproject.toml`, and one top-level
`CHANGELOG.md`. Individual modules and stories do not carry their own version or changelog.

## Writing standards

- Imperative mood, active voice: "Run the command", "Create the file" — never "You should run".
- Be specific, never vague: "Use `snake_case`" — not "use good naming".
- State exact versions in setup docs (the dependency table lives in `external-libraries.md`;
  do not duplicate it loosely in prose elsewhere).
- Use real field names and real module paths, never `foo`/`bar` placeholders.
- Prefer tables for structured data over bullet lists.
- One sentence per line where practical, for cleaner diffs.
- Use strict heading hierarchy — never skip a level.
- Specify the language on every fenced code block.
- Never duplicate information across files — link to the authoritative source instead (for
  example, a document needing the dependency table links to `external-libraries.md` rather
  than re-listing package versions).

## Diagrams

Use Mermaid for any diagram expressible as one — flowcharts, sequence diagrams, state
machines. Do not commit a PNG/JPEG for content a Mermaid diagram could carry instead.
